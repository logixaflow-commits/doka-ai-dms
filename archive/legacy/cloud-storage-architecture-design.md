# Doka Cloud Edition Storage Architecture Specification

**Date:** 2026-10-05

## Goal

Replace the current Supabase-only binary storage path with a provider-routed Cloud Edition storage architecture while keeping Supabase as the metadata/control plane, preserving single-user authorization and RLS, avoiding Worker byte proxying, and remaining compatible with free-tier constraints.

## Agreed storage policy

| Artifact | Primary storage | Rule |
|---|---|---|
| Document thumbnails, covers, preview images | Cloudinary | Image derivatives under 10 MB; use transformations |
| Small documents, OCR text, extracted chunks | Supabase Storage | Document source objects up to 50 MiB |
| Large documents, scanned PDFs, EPUBs, archives | Backblaze B2 | Source objects over 50 MiB; B2 is source of truth |
| Document exports, backups | Google Drive | User-owned export/backup destination only |

The existing 50 MiB Supabase object limit is not removed. It becomes a routing boundary.

## Local and hybrid provider modes

`STORAGE_PROVIDER=mock` is a supported local-test mode. Mock providers use in-memory metadata and local-filesystem bytes and require no cloud credentials or network access.

`STORAGE_PROVIDER=hybrid` is the real-credential mode. It enables the provider router for configured Supabase, Cloudinary, B2, and Drive capabilities; a provider with incomplete credentials fails closed rather than pretending to be production-ready. The mode may still use mock providers for explicitly disabled/unconfigured local capabilities, but production readiness requires the real provider gates.

The default for existing documents is `storage_provider=supabase` so the migration is backward-compatible.

## Routing rules

1. Original/source document objects at or below 50 MiB route to Supabase Storage.
2. Original/source document objects above 50 MiB route to Backblaze B2.
3. Thumbnail/cover/preview image artifacts under 10 MB route to Cloudinary.
4. If Cloudinary credit/usage guard reports the configured low-credit condition, new image derivatives fall back to Supabase Storage and the API returns a non-sensitive warning indicator for the UI.
5. Cloudinary is never the source-of-truth location for original documents.
6. Google Drive is never the primary document store.
7. No provider secret is exposed to the browser.

## StorageProvider contract

Introduce a provider-neutral interface used by routing and document services.

Required operations:

- `create_upload_session(metadata) -> UploadSession`
- `get_signed_upload(session) -> SignedUpload`
- `complete_upload(session, client_result) -> StoredObject`
- `get_signed_download(object_ref, expires_seconds) -> SignedDownload`
- `delete(object_ref) -> None`
- `head(object_ref) -> ObjectInfo`
- `initiateMultipartUpload(metadata) -> MultipartUpload`
- `uploadPart(upload, part_number, checksum, signed_request) -> PartReceipt`
- `completeMultipartUpload(upload, parts) -> StoredObject`
- `abortMultipartUpload(upload) -> None`

The multipart operations are mandatory in the interface even when a provider does not require multipart for a particular object size. The B2 implementation must support multipart uploads for files above 5 GB.

All completion paths verify the authoritative object size and SHA-256 before metadata is marked ready. A checksum mismatch rejects the object and leaves metadata non-ready/quarantined.

## Backward-compatible migration and rollback

The metadata migration is additive. The first migration phase is read-only with respect to existing object bytes: it adds provider metadata with `storage_provider=supabase` for existing rows and does not copy, delete, or rewrite their objects.

Existing documents are lazy-migrated only when they are accessed or explicitly transitioned. A document remains Supabase-backed until the new provider object is verified by size and SHA-256 and the metadata transition is committed.

Rollback is provider-routing rollback, not destructive data movement: switch the router to Supabase-only, pin new writes to Supabase, and continue reading existing Supabase objects. Previously migrated provider metadata remains recorded for later reconciliation; rollback must never require deleting the original Supabase object.

## Provider implementations

### Supabase Storage

Use authenticated, short-lived signed upload URLs so the browser sends bytes directly to Supabase Storage. The Worker only creates the upload session, authorizes ownership, and records completion metadata.

The Supabase provider is limited to the configured 50 MiB source-object boundary.

### Backblaze B2

Use B2's S3-compatible API with short-lived SigV4 presigned requests generated server-side.

For objects above 5 GB, use multipart upload with the required initiate/upload-part/complete/abort lifecycle. The Worker must never buffer the full object or proxy its bytes.

B2 credentials remain server-side secrets.

### Cloudinary

Use signed browser upload parameters generated by the Worker. Store only image derivatives/preview artifacts, not original documents.

Cloudinary transformations are requested through provider-specific signed parameters. The provider returns an opaque asset reference that is stored in document metadata.

A server-side usage/credit guard is checked before issuing a new derivative upload session. The low-credit threshold is configurable and must default to a conservative failover threshold. When the guard blocks Cloudinary, the same derivative is routed to Supabase Storage and the response includes a stable warning code such as `cloudinary_credit_fallback`.

### Google Drive

Google Drive is an export/backup target. It receives explicit user-requested exports or backup bundles/manifests and is not part of normal source-document upload routing.

Drive OAuth refresh tokens remain server-side. Export/backup operations are idempotent and record the remote file ID, checksum, size, export/backup timestamp, and status.

## Metadata model

Supabase remains the metadata/control plane.

Extend document/version metadata to represent:

- `storage_provider`
- `object_key`
- `size_bytes`
- `content_type`
- `sha256`
- `version_no`
- `storage_status`
- `storage_region` when applicable
- preview/thumbnail provider and object references
- export/backup provider reference and status

Existing owner/document/version relationships remain authoritative. New provider metadata must remain owner-scoped by the existing RLS policies.

## Browser upload flow

1. Browser authenticates with Supabase Auth.
2. Browser requests an upload session with filename, MIME type, expected size, and SHA-256.
3. Worker authenticates the user and applies routing policy.
4. Worker returns only the provider-specific short-lived signed upload instructions.
5. Browser uploads directly to Supabase, Cloudinary, or B2.
6. Browser sends completion information.
7. Worker verifies object existence, size, and checksum using provider APIs.
8. Worker writes/updates Supabase metadata.
9. UI refreshes from metadata and never receives provider secrets.

Large uploads must not pass through the Worker.

## Security requirements

- Preserve Supabase RLS and owner isolation.
- Preserve the configured single-user email allowlist.
- Never expose Supabase service-role keys, B2 credentials, Cloudinary API secrets, or Google Drive refresh tokens.
- Signed upload/download URLs must be short-lived and scoped to the authorized object.
- Object keys must remain owner-scoped and path-safe.
- Completion endpoints must be idempotent and reject ownership mismatches.
- Failed checksum verification must not produce a ready document.
- Provider errors must not leak credentials, authorization headers, raw upstream bodies, or internal object paths beyond the minimum metadata needed by the client.

## Cloudinary credit guard

The Worker uses Cloudinary usage/quota information through a server-side credentialed path. It must not expose the Cloudinary API secret or raw account usage response to the client.

Configuration includes:

- `CLOUDINARY_CLOUD_NAME`
- `CLOUDINARY_API_KEY`
- `CLOUDINARY_API_SECRET`
- `DOKA_CLOUDINARY_LOW_CREDIT_THRESHOLD`

The guard is fail-closed for Cloudinary derivative creation when usage cannot be safely determined, and falls back to Supabase for supported derivative artifacts. The UI receives only a stable warning state.

## B2 quota guard

The B2 provider exposes usage information to a server-side quota guard. Configuration defaults are:

- `DOKA_B2_WARNING_PERCENT=80`
- `DOKA_B2_BLOCK_PERCENT=95`
- optional `DOKA_B2_QUOTA_FALLBACK=google_drive`

At 80%, the system emits an operator/admin warning. At 95% or higher, new B2 source-upload sessions are blocked. Unknown or stale usage is fail-safe and must not authorize a new B2 upload when the system cannot establish that the quota is below the block threshold.

When the optional Google Drive fallback is explicitly enabled and available, a blocked B2 upload may be routed through an emergency Drive path. The UI receives a stable warning code such as `b2_quota_fallback_google_drive`. Drive fallback is never silent and does not make Google Drive the normal source store.

## Free-tier and quota guards

- No paid-only dependency is required.
- Supabase source objects remain capped at 50 MiB.
- Cloudinary derivative uploads remain capped at 10 MB.
- B2 is used only when the source-object routing rule requires it.
- Upload sessions reject impossible/oversized requests before issuing signed credentials.
- Provider usage checks and configurable thresholds prevent accidental Cloudinary overuse.
- No new Redis/QStash dependency is introduced solely for storage routing.

## Mock, migration, and quota testing requirements

The implementation must also include tests for:

1. `STORAGE_PROVIDER=mock` works without cloud credentials and uses deterministic in-memory/local-filesystem providers;
2. `STORAGE_PROVIDER=hybrid` selects real providers when credentials are present and fails closed when required credentials are incomplete;
3. existing documents receive `storage_provider=supabase` without object-byte migration;
4. lazy migration preserves Supabase reads until a provider transition is verified;
5. rollback to Supabase-only requires no object deletion or byte copy;
6. B2 usage at 80% produces an operator warning;
7. B2 usage at 95% blocks new B2 source uploads;
8. unknown/stale B2 usage fails safe;
9. explicit Google Drive quota fallback is visible, opt-in, and does not silently alter the normal source-of-truth policy.

## Testing requirements

The implementation must include tests for:

1. source object <= 50 MiB routes to Supabase;
2. source object > 50 MiB routes to B2;
3. preview image < 10 MB routes to Cloudinary;
4. Cloudinary low-credit condition routes a preview derivative to Supabase and returns the warning code;
5. Cloudinary usage lookup failure does not expose provider credentials;
6. browser upload sessions are signed, short-lived, owner-scoped, and never contain service secrets;
7. B2 multipart initiate/upload-part/complete/abort lifecycle;
8. files above 5 GB never cause Worker-side buffering;
9. SHA-256 mismatch prevents metadata from becoming ready;
10. signed download access is denied for another owner;
11. provider failures are translated into safe API errors;
12. version creation and restore preserve provider/object/checksum metadata;
13. Google Drive export/backup is idempotent and records remote references;
14. single-user authorization remains enforced;
15. existing Supabase RLS/security tests remain green.
16. mock/hybrid mode and migration rollback tests remain green.
17. B2 quota warning/block/fallback tests remain green.

## Deployment boundary

- Vercel remains intentionally paused and must not be reactivated as part of this work.
- Cloudflare Worker deployment is not performed until the required B2, Cloudinary, and Google Drive production credentials are configured and the production readiness gate passes.
- Documentation must distinguish implemented code paths from credentials/configuration that remain operator-supplied.

## Out of scope

- Making Google Drive the primary source store.
- Proxying large file bytes through Cloudflare Worker.
- Disabling RLS or replacing the single-user authorization guard.
- Adding a paid storage/queue service solely to implement this architecture.
- Enabling or deploying Vercel.
